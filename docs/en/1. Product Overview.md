# Agent Security

Agent Security is openJiuwen's collection of security capabilities for agent scenarios.

What sets an agent apart from an ordinary program is that it turns model output into real actions: running shell commands, reading and writing files, reaching the network, and starting child processes. One injected instruction, or one bad model decision, can end in a deleted directory, an exfiltrated key, or a modified system configuration. A check at a single point is not enough: the system needs a decision before the action, isolation during execution, detection while it runs, and control over credentials and outbound text.

This repository puts five capabilities in one tree. Each is installed and run on its own:

- **Agent SSAS** sees what happens at runtime.
- **JiuwenBox** controls the execution environment.
- **agent-shield** decides a single action.
- **Security Gateway** stores sensitive credentials.
- **Security Mask** redacts outbound text.

A few abbreviations first: SSAS stands for Security Situation Awareness System; OCSF is the Open Cybersecurity Schema Framework, a common field standard for security events that makes alerts easier to feed into a SIEM; a Rail is a hook in agent-core attached to the agent lifecycle.

## 1. Components at a glance

| Component | Directory | Problem it solves | Delivery form |
| --- | --- | --- | --- |
| Agent SSAS | `agent_ssas/` | Agent behavior is invisible, so incidents are hard to trace | Python package; in-process library or standalone HTTP service |
| JiuwenBox | `jiuwenbox/` | Agent commands run directly on the host, so privilege abuse and destructive writes are hard to contain | Standalone service with REST, CLI, and MCP |
| agent-shield | `agent_shield/` | Tool calls have no shared allow / ask / deny decision | In-process SDK plus native Windows guard binaries |
| Security Gateway | `security_gateway/` | API keys and tokens sit in plaintext on disk | Python library for encrypted field storage and key rotation |
| Security Mask | `foundation/` | Streaming output carries keys, phone numbers, and other sensitive spans | Python library for regex-based streaming masking |

```text
agent-security/
├── agent_ssas/        situational awareness: events, detection, OCSF logs
├── jiuwenbox/         sandbox service: isolated execution on Linux and Windows
├── agent_shield/      in-process decisions: policy engine, tool permission, native guards
├── security_gateway/  encrypted field store: schema, keys, rotation
├── foundation/        streaming masking utility (security-mask)
└── docs/              this directory
```

## 2. Where each component sits in one tool call

Suppose a user tells the agent: "Tidy up this repository, then push it." The agent decides to call a shell tool. Several things can happen next:

1. **agent-shield decides first.** It normalizes the tool name and arguments into an event, then matches built-in rules, third-party rules, user rules, and existing grants. For example, `git push --force` hits the force-push rule and returns `ask`; `rm -rf ~` hits the outside-workspace forced-delete rule and also returns `ask`. A `deny` comes from critical behaviors such as writing protected files or raw disks.
2. **The host handles ask.** If the result is `ask`, the host opens an approval window. Approving releases this one call; rejecting turns it into `deny`.
3. **Security Gateway supplies credentials.** If the command needs an external service, the key is read from the encrypted field store first. What lands on disk is ciphertext, and the key is derived from shards and can be rotated.
4. **JiuwenBox executes.** The command runs inside a sandbox: bubblewrap with namespaces, Landlock, and seccomp on Linux; restricted tokens, a Job object, WFP, and NTFS ACLs on Windows. The policy decides which directories are readable, which endpoints are reachable, and whether deletion is allowed.
5. **Agent SSAS records and detects.** Lifecycle events such as `invoke_start`, LLM input/output, and tool input/output go into the detection engine, which produces a risk assessment and OCSF threat logs. The default policy is `observe_only`, which records but does not block. Even under `active_protection`, a failure inside the detection path does not block the caller; that is intentional fail-open.
6. **Security Mask handles outbound text.** If the result is rendered in a web chat window, regex matches are replaced with stars as the stream flows, so keys or personal data do not appear in the clear.

These steps are not tightly coupled. You can use agent-shield alone for decisions, or JiuwenBox alone for isolation; install as many layers as you need.

## 3. Component details

### 3.1 Agent SSAS: see what the agent did

Agent SSAS is a security situational awareness system. It collects events from the agent runtime, sends them through pluggable detection modules, and writes the result as OCSF threat logs backed by SQLite.

- **What it collects**: six lifecycle events (`invoke_start`, `llm_input`, `tool_input`, `tool_output`, `llm_output`, `invoke_end`) plus one security-derived event (`permission_interrupt_tool`, another security rail's interception result).
- **How it detects**: a detection module declares in `module.yaml` which events it subscribes to and which data-modeling and threat-analysis plugins it uses. Built-in modules are `agent_moss` and `security_rail_detection`; `test_detection` is off by default.
- **How it runs**: `inprocess` mode runs detection in the current process with no network hop; `http` mode starts a FastAPI service (default `0.0.0.0:8443`) shared by several agents.
- **How it decides**: the default is `observe_only`, which records everything and allows all calls; `active_protection` blocks critical findings, alerts on high / medium / low, and allows safe results.
- **What happens on failure**: initialization errors, malformed events, and detection timeouts do not stop the caller. That is fail-open, and it applies only to failures in the detection path itself. Once detection produces a critical finding, `active_protection` still blocks. This keeps security observation from becoming a single point of failure without giving up real blocking capability.

**Use it when** you need to audit agent behavior, detect threats, and keep a traceable log without changing the agent's main flow.

### 3.2 JiuwenBox: put commands in a sandbox

JiuwenBox is a sandbox service. Callers create a sandbox, transfer files, and run commands over REST, CLI, or MCP, and a policy file decides the isolation details.

- **On Linux**: bubblewrap starts the sandbox process, optionally with network namespaces, Landlock, seccomp, cgroups, namespace limits, and capability limits.
- **On Windows**: a restricted token launches the process in two hops, a Job object caps memory, CPU, and process count, WFP controls egress, a loopback proxy filters domains, IPs, and ports, and NTFS ACLs control reads and writes.
- **How policy applies**: the server loads a root policy at startup; a sandbox can override or append to it at creation. Fields such as `read_only` / `read_write`, `bind_mounts`, `network`, and `windows` determine the effective permissions.
- **How deletion works**: with `JIUWENBOX_SOFT_DELETE=1` on Windows, deletes go to the recycle bin first; if that fails, they move to an archive directory on the same volume instead of deleting permanently.
- **What happens on failure**: an unprepared environment, a missing required ACL, or an unavailable Landlock under `hard_requirement` fails the create or start instead of degrading silently.

**Use it when** the agent must run untrusted commands, process external files, or reach the network, but those actions need to stay within a controlled boundary.

### 3.3 agent-shield: decide before execution

agent-shield is an in-process security decision SDK. It does not call a model and does not use the network. It does three things:

- **Action decisions**: `tool_permission/` returns a deterministic allow / ask / deny for one tool call, covering commands, paths, outbound endpoints, host checks, and deletion guards.
- **Behavior policy**: `policy_engine/` is the policy decision point, with four rule layers, ten priority levels, `Decide` settlement, and a loopback HTTP service. Third-party rules register through the ruleset interface; user rules and grants come from the host.
- **Content detection**: `detection/` checks content entering a model or coming back as a tool result for prompt injection and similar risks, and returns a probabilistic soft signal; the caller decides whether to stop.

On Windows, two native guards intercept file, process, and network access before execution:

- **Process guard**: `wrap()` starts a standalone `process_guard.exe` and asks for decisions over a JSON pipe; it supports recycle-bin deletion and x86 WOW64 children.
- **DLL guard**: `RuntimeGuardManager` in the host process injects `jiuwen_runtime_guard.dll` and communicates over binary frames; it supports in-flight approvals, grant reuse, and foreground/background process trees.

**Use it when** you need one consistent decision before a tool call or system call, with results that are explainable, auditable, and able to trigger human approval.

### 3.4 Security Gateway: store sensitive fields encrypted

Security Gateway is an encrypted field store library. It stores records by id, and the schema decides which fields are encrypted.

- **Schema**: the host declares in code which fields a record has, each field's type, and whether it is encrypted.
- **Keys**: a data encryption key (DEK) encrypts fields, and a key encryption key (KEK) wraps the DEK. The KEK is derived with PBKDF2 from the XOR of three shards: a file, SQLite, and a built-in constant.
- **On disk**: record fields are encoded into a `VREC` container and stored in `vault_record.data`; the schema, key metadata, and sync state sit in the other three tables.
- **Rotation**: manual rotation, automatic rotation, and takeover of an interrupted rotation are supported.
- **Boundary**: it opens no port and is not a full credential-routing service; HTTP APIs, credential routing, and LLM-gateway integration belong to the consuming application.

**Use it when** you need to keep API keys, tokens, private keys, and similar fields on local disk with a clear encryption boundary and a rotation mechanism.

### 3.5 Security Mask: replace sensitive spans in a stream

Security Mask is a small streaming masking utility. The caller supplies regexes, and the tool replaces matched spans as characters flow through.

- A match of 11 or more characters keeps its first 3 and last 4 characters; a match of 5–10 characters shrinks the head and tail so at least 4 characters stay hidden; a match of 4 characters or fewer is replaced entirely. The middle is always four full-width stars (`＊＊＊＊`).
- While streaming, each `push` sends everything up to and including the last delimiter through replacement and keeps the remainder pending; `finish` flushes the last pending part. A delimiter is any character outside `A-Za-z0-9._-+/=@%`, so a key split across chunks is not half-revealed.
- The caller owns the rules and the switch; the utility does not decide what counts as sensitive.

**Use it when** a web chat, log echo, or another incremental renderer needs a final masking layer before text reaches the user.

## 4. How to choose

| What you need | Start with |
| --- | --- |
| Visibility into what the agent did at runtime | Agent SSAS |
| A controlled environment for dangerous commands | JiuwenBox |
| allow / ask / deny before a tool call | agent-shield |
| Encrypted storage for API keys and tokens | Security Gateway |
| Masking of streaming text in a web channel | Security Mask |

The components can be combined. A common setup is: agent-shield decides, JiuwenBox executes, Agent SSAS records and detects, Security Gateway holds credentials, and Security Mask masks outbound text.
