剥壳与拆子命令

权限视图如何得到 original / unwrapped / subcommand · 不改真实执行参数

先分清概念（不要混）
Shell 入口：tool_name 是否走进「剥壳 / 展开」流水线（看工具名名单）。
Shell 解析器：命令串里的启动器形态（如 bash -c、cmd /c、pwsh -Command）——剥壳认这个。
命令（payload）：真正执行的叶子（如 ls、rm、Get-ChildItem）。
产品入口工具卡：Agent 送来的 tool_name（如 bash、mcp_exec_command）。有的卡名看起来像解析器，有的只是代跑入口；不等于串里的解析器。
两张表 + 按方言拆（已落地 Phase 1）
表代码职责
A · 命令入口routing._COMMAND_ENTRY_TOOLStool_name 是否进入剥壳/展开
B · 解析器启动器canonicalize 正则命令串里剥谁

流程：① 入口表判定 → ② 保留 ORIGINAL → ③ 剥壳（有则 UNWRAPPED）→ ④ 对权限视图按方言拆子命令（无 SHELL_TOOLS 五元组门禁）→ ⑤ 组件取最严。
Phase 1 拆分后端：仅 posix_shell / unknown 走 bash AST；PowerShell / CMD 拆分属 Phase 2。

1. 命令入口名单（表 A）

判定：tool_name basename ∈ _COMMAND_ENTRY_TOOLS（is_shell_tool）。 是 → 剥壳/展开；否 → 仅 original。

认的是工具名。不会把 mcp_exec_command 改成 bash；只对它的 command 串剥壳/拆分。

分组tool_name（穷举）方言
POSIX 名 bash · sh · zsh · ksh · dash · ash · fish posix_shell
PowerShell 名 powershell · powershell.exe · pwsh · pwsh.exe · core.powershell powershell
CMD 名 cmd · cmd.exe cmd
代跑入口 mcp_exec_command · create_terminal args：shell / shell_type / executable / interpreter；否则 unknown

例：/usr/bin/bash → 入口。read_file → 非入口。

2. Shell 解析器名单（剥壳认谁）

剥壳盯的是命令串里的解析器启动形态，不是 Agent 工具名，也不是 ls 这类 payload。

方言解析器（启动器）典型启动形态
CMD cmd · cmd.exe /c 或 //c + 引号串 / 无空格裸串
PowerShell powershell · powershell.exe · pwsh · pwsh.exe 中间可夹 -Xxx，再 -Command / -c + 引号串 / 裸串
POSIX bash · sh · zsh · dash · ash（可带路径 / .exe / 引号路径） 行首或紧跟 ; & | ( ) 之后；中间可夹开关；再带字母 c 的短选项（-c/-lc/-cl/-ic…）+ 引号串 / 裸串

ksh / fish 等若要支持剥壳，应显式加入上表；主流解析器都支持某种复合命令，差别在语法方言，不是「能不能复合」。

3. 剥壳（遇解析器 → 生成内层命令）

函数 canonicalize_shell_command_for_permission：整串最多剥 1 层；剥完 ≠ 原文才追加 unwrapped。无外壳时原文即权限视图，不产生 unwrapped。

会剥例 → 剥壳后
CMDcmd /c "dir C:" → dir C:
PowerShellpwsh -c 'Get-Date' → Get-Date
powershell -NoProfile -Command '…' → 内层
POSIX -cbash -c 'rm x' → rm x
sh -lc "rm -rf /" → rm -rf /
/bin/zsh -c 'rm x' → rm x
bash --norc -c 'rm x' → rm x
cd d && bash -c 'rm x' → cd d && rm x
不会剥说明
无外壳ls -la、rm -rf /tmp、ls; rm x —— 仍可继续拆子命令
外壳不在命令位echo bash -c 'rm' 保持原样（防误剥）
第二层只剥一层，不递归

4. 拆子命令（对原文或剥壳后的串）

不是 split(';') / 按分隔符傻切。叶子来自语法解析；失败则不产生 subcommand。 不以「是否剥成功」、也不以 SHELL_TOOLS 五元组为拆分资格。
  • 输入：canonical（剥壳后；无外壳则原文）。
  • Phase 1 方言门控：supports_posix_subcommand_split — 仅 posix_shell / unknown 调用 bash AST（tree-sitter bash + 保守 fallback）。
  • Phase 2（未做）：PowerShell / CMD 专用拆分后端。
  • 对象：payload 叶子（ls / rm…），不是再识别解析器。
解析结果引擎行为含义
simple + 多条叶子
（或一条叶子 ≠ 整串）		 追加 subcommand×N 如 ls; rm x → ls、rm x
simple + 仅一条且 = 整串 不追加 与 original/unwrapped 重复
too_complex 不追加 $(…) / 子 shell / heredoc / 命令组等；结构底线可另抬等级
parse_unavailable 不追加 后端不可用或无法安全分析

剥壳未覆盖：ksh -c / fish -c（入口可有其名，表 B 不剥）。fallback 不会按 ; 切开。

2. TieredPolicyComponent

命令 / 工具分层策略 · 默认参与 · shell 工具含结构底线

看哪些候选
原文 / 剥壳 / 子命令都会跑 approval→rules→tools→defaults（及 shell 零配置兜底）。 结构底线只在原文与剥壳上跑，子命令不跑。非 shell 工具也可走本组件（无结构底线，无规则时可弃权）。

2.1 判定顺序与结构底线

组件内顺序（未短路时）
1. approval_overrides
命中 → ALLOW（仅 action=allow 生效；引擎层还可对整条/剥壳整调用短路）
2. rules（builtin + 用户）
同时匹配取最严；可用同 pattern 覆盖内置 action
3. tools.<name>
整工具基线（含 deny，无早退）
4. defaults.*
全局默认
5. shell 兜底 ASK
非 shell 可弃权（None）
结构底线（仅 shell · 原文/剥壳）
作用
规则比的是看得见的文本；底线拦「解析看不清 / 运行时才长出文本」的结构风险。先走左侧判定，再只抬不降。
何时跑
shell 工具名 + 原文/剥壳候选 + 命令非空；子命令候选不跑；approval 整调用短路时整段不跑。

结构底线说明

AST = Abstract Syntax Tree（抽象语法树），不是「子命令」的简称。用 AST（优先 tree-sitter bash，没有则保守扫描）解析整条命令；能拆时才得到子命令列表。底线看的是整条/剥壳的结构，不会对每个子命令再跑一遍。

四类检查写死都会做（命中后的等级见后文 guard_actions，缺省 ask）。对照例子：

  • too_complex — 解析器认为结构不可信、不宜当普通命令拆。
    例：语法破损的命令；或含 $(…) / 子 shell / 命令组等复杂结构时，tree-sitter 常直接标 too_complex（可与下面 structure_guard 同时命中）。
  • parse_unavailable — 没有可靠 AST（常见：未装 tree-sitter，走降级扫描），且原文带风险结构特征。
    例：降级路径下 echo hi > f.txt（含重定向等特征，扫描器不敢当 simple）。注意：这里抬的是「解析不可用」档；重定向目标路径仍归 FileGuard，不是 structure_guard。
  • structure_guard — 命令替换 / 进程替换 / heredoc（故意不含单独的 > >> < 重定向）。
    例：echo $(whoami)；cat <(echo x)；cat <<EOF … EOF。
    反例：echo hi > /tmp/a 不靠本项拦写文件（路径侧处理）。
  • interpreter_sink — 管道把数据喂给解释器（非首段是 bash/sh/python/node/pwsh 等）。
    例：curl http://x | bash → 命中。
    反例：ls | wc -l → 下游不是解释器，不命中。

安全例：ls / echo hello → 解析 simple 且无上述特征 → 底线空，结论完全由左侧规则链决定。

2.3 规则字段与示例

rules[] / approval_overrides[] 元素结构

规则对象字段
字段可取值 / 默认
idstring，可选；用于日志标签
tools具体工具名列表，如 [bash, powershell]。不支持类别词 shell
pattern匹配串。前缀 re:=正则；含通配符=通配；否则全等
match_type见下方说明
actionallow / ask / deny。有 action 时优先，不走 severity
severity仅无 action 时生效；换算见上方「severity × permission_mode」表
layerbuiltin → 内置层；其它值或缺省 → 用户层（影响归类与「同 tools+pattern 覆盖内置 action」）
match_type 做什么：不是「怎么匹配 pattern」的开关，而是这条规则要不要进 TieredPolicy。 缺省或 command → 参与命令文本匹配；写成其它值（如历史遗留的 path / network）→ 本组件整条忽略（等于没配）。 pattern 本身怎么比，看有没有 re: / 通配符 / 全等，与 match_type 无关。
layer 做什么：配置加载时把 rules 拆成内置层与用户层。 layer: builtin 归内置（也可被 package_builtin_rules 控制）；用户规则若与某条内置规则相同 tools + pattern且带 action，则只覆盖该内置的判罚，不是按 id 覆盖。
示例（覆盖上表全部键与可取值）
# permission_mode: normal | strict
permission_mode: normal
# package_builtin_rules: true | false | "0"|"false"|"no"|"off"
package_builtin_rules: true

# tools 值: allow | ask | deny；亦可 bash: {"*": "allow"}
tools:
  bash: allow
  powershell: ask
  mcp_exec_command:
    "*": deny

# defaults["*"]: allow | ask | deny | undetermined
defaults:
  "*": ask

rules:
  - id: block_curl_pipe
    layer: user                  # 非 builtin / 缺省 → 用户层
    tools: [bash, powershell]
    pattern: "re:curl.+\\|\\s*sh"   # re: 正则
    match_type: command          # 缺省同此；本组件只认 command
    action: deny                 # allow | ask | deny
  - id: warn_rm_rf
    tools: [bash]
    pattern: "rm -rf *"             # 通配
    match_type: command
    severity: HIGH             # 无 action 时走 severity×mode 表
  - id: exact_echo
    tools: [bash]
    pattern: "echo hello"          # 全等
    action: allow
  - id: package_sample
    layer: builtin               # 归内置层
    tools: [bash]
    pattern: "re:^sudo\\b"
    match_type: command
    action: ask
  - id: ignored_path_rule
    tools: [bash]
    pattern: "/etc/*"
    match_type: path             # ≠ command → Tiered 整条忽略
    action: deny

approval_overrides:                   # 同规则形；仅 action=allow 生效
  - id: remember_rm_tmp
    tools: [bash]
    pattern: "rm -rf /tmp/ok"
    match_type: command
    action: allow

# guard_actions 四键均要可配：allow | ask | deny
guard_actions:
  too_complex: ask
  parse_unavailable: ask
  structure_guard: deny
  interpreter_sink: allow

# 旧版键；可被上面 guard_actions 覆盖
shell_guard:
  unknown_structure: true             # false → too_complex/parse_unavailable 视为 allow
  interpreter_sink: true              # false → interpreter_sink 视为 allow

4. FileGuard

可配置路径防护 · 默认需显式启用或存在 external_directory / trusted_dirs

看哪些候选
只看原文 / 剥壳；子命令弃权（路径在整视图抽取）。非 shell 工具通常只有原文候选。
FileGuard 配置
键类型 / 可取值默认
file_guard.enabled bool 未写：有 external_directory 或 trusted_dirs 则 true，否则 false
file_guard.defaults read/write/exec → allow|ask|deny 各轴 ask（启用时）
file_guard.workspace read/write/exec → allow|ask|deny 无。只配三轴策略，不写路径；路径 = 运行时 workspace 根
file_guard.paths[] path · match(prefix|glob) · read/write/exec []
external_directory str 或 map（顶层键，不在 file_guard 内） 无。旧版顶层配置，见下方说明（动作须显式写 allow/ask/deny）
composition.source_order list[str] 顶层键（与 file_guard 同级）。无则普通判定（所有 paths 混比）。 出现 composition 则进入多层叠加：合法层名仅 user / cloud / builtin（对应 path 规则上的 layer）。 列表顺序 = 判定顺序：任一命中层 deny 立刻生效 → 否则取第一个有命中的层内最长前缀/最严 → 都未命中才走 defaults。 列表含 user 时才纳入 runtime.trusted_dirs 与旧 external_directory 迁移。
示例
file_guard:
  enabled: true                    # true | false
  defaults:                         # 轴值: allow | ask | deny
    read: ask
    write: deny
    exec: ask
  workspace:
    read: allow
    write: allow
    exec: allow
  paths:
    - path: "**/.ssh/**"
      match: glob                 # glob | prefix
      read: ask
      write: deny
      exec: deny
    - path: "/etc"
      match: prefix
      read: ask
      write: deny
      exec: deny
external_directory:                 # 旧版顶层键：str 或 map
  "*": ask
  "/tmp/share": allow
composition:                       # 可选；多层策略才需要
  source_order: [user, cloud, builtin]

# 宿主注入（通常不写进业务 yaml）
runtime:
  workspace_root: "/path/to/ws"
  # 或优先用 project_root（见下）
  trusted_dirs: []

file_guard.workspace · 策略轴绑定

语义：声明工作区根目录上 read / write / exec 的 PermissionLevel；配置对象不含路径字段。 路径在配置编译期由 runtime_workspace_root(config) 解析，再生成一条 match=prefix 的 FileGuardPathRule。

项契约
配置形态 { read?, write?, exec? }，取值 allow|ask|deny；缺轴按编译默认补齐
根路径来源 runtime.project_root 优先，否则 runtime.workspace_root；由宿主在 update_config 写入 config["runtime"]
编译产物 prefix(resolved_root) → (read, write, exec)，并入生效 paths 规则集
根缺失 已配置 workspace 但根未解析成功：记 WARN，丢弃本条规则；不改变 FileGuard enabled 及其余规则
判定范围 命中该前缀的访问使用本轴；未命中则继续 defaults / 其它 paths / 迁移规则

示例：file_guard.workspace = {read:allow, write:allow, exec:allow} 且 runtime.workspace_root = "/data/ws" ⇒ 对 /data/ws/** 三轴 ALLOW。

external_directory · 旧版顶层配置（与 file_guard 同级）

为兼容旧 permissions 形态保留。等级须显式给出，值域 allow|ask|deny；不存在隐式「一律拒绝 / 一律放行」。

新配置应直接写 file_guard.defaults + workspace + paths；本键仅作迁移与回退。

形态编译语义
string 例如 ask：默认档读 / 写 / 执行三轴同为该等级。已写 file_guard.defaults 时本值只作缺省回退
map["*"] 未命中更具体路径时的默认档；合法值 allow|ask|deny → 读 / 写 / 执行三轴同值
map[path] path 为目录前缀（如 /tmp/share: allow）：
  • allow → 读 allow、写 allow、执行 ask
  • ask / deny → 读 / 写 / 执行三轴同为该值
与 file_guard.paths 并存时迁入 paths；同前缀已有条目则跳过
与 enabled / 现行 file_guard 的关系行为
enabled 缺省 显式 file_guard.enabled 优先；未写时：配了 external_directory，或宿主传了 trusted_dirs ⇒ 打开 FileGuard
仅配置本键 按旧规则编译：① 工作区根 → 读/写/执行全 allow；② "*" / 字符串 → 默认档；③ 本键里的具体路径 → 前缀规则（权限见上表）
与 file_guard.* 并存
  • 已写 file_guard.defaults → 用它；没写才用本键的 "*" / 字符串补默认档
  • 先用 file_guard.paths / workspace；再把本键的具体路径补进去；同一前缀已有规则则跳过（以 file_guard 为准）
runtime.trusted_dirs 宿主传入的额外信任目录（常见：/add-dir）。每条编成前缀规则：读 allow、写 allow、执行 ask。

6. HostGuard

默认关闭 · 开启后参与取最严 · 命中一律 DENY

看哪些候选
仅 shell，且工具名在安全名单（bash / powershell / mcp_exec_command）。 原文 / 剥壳 / 子命令都会跑（不按 kind 弃权）。非 shell 弃权。

怎么匹配

输入：工具参数里的命令字符串（command / cmd）。匹配方式：子串正则 / 切段解析，要求「杀进程类命令」与「受保护名字」在同一段里同时出现。

  • 内置形态（enabled: true 即生效）：pkill|killall|kill +（中间可有参数，遇 ; | & 换行断开）+ jiuwenswarm|jiuwenclaw
  • pkill -f jiuwenswarm → DENY（要同时有 pkill 与 jiuwenswarm）
  • pkill nginx → 放行本规则；echo jiuwenswarm → 放行本规则
  • 切段：按 ; && | 切开后，段首是 kill 族且段内带受保护名 → DENY
配置项
键默认开了拦什么 / 怎么判命中例
host_guard.enabled false 总开关；false → 组件不装载 —
host_guard.protected_patterns 内置 6 条 整段命令正则，元素 {pattern, reason}。缺省 6 条： pkill|killall|kill×jiuwenswarm|jiuwenclaw，以及 jiuwenswarm … | xargs kill。 写出本键 = 只用你的列表做整段正则（内置 6 条不再参与）。 另有切段规则（段首 kill 族且段内含 jiuwenswarm/jiuwenclaw）始终生效，不由本键控制。 pkill -f jiuwenswarm
host_guard.shell_mismatch true 仅工具名 bash：命令文本像 PowerShell（Cmdlet / $env: 等）→ DENY bash + Get-ChildItem
host_guard.worktree_guard true 防 Agent 用 git worktree add <path> 在 runtime.workspace_root 外再建可写工作树（绕开工作区边界）。 目标必须在 workspace 内；路径解析失败也 DENY。 git worktree add ../outside → DENY；git worktree add .worktrees/f → 放行本项
host_guard.python_name_kill false 段首为 kill 族，且目标名像 python（非纯 PID）→ DENY pkill python · taskkill /IM python.exe /F
host_guard.backend_pid_kill false 防按数字 PID 杀掉宿主后端 / 当前权限进程。 从命令抽出目标 PID，与运行时集合求交：① 当前进程；② 其祖先（需 psutil）；③ cmdline 像 JiuwenSwarm 后端的进程（如 -m jiuwenswarm.app、jiuwenswarm-agentserver、 --desktop-run-agent 等，见代码 _BACKEND_*）。 PID 名单运行时扫描，配置里不写死。 kill 12345 / taskkill /PID 12345（12345 落在上述集合时）
host_guard.whole_line_regex false 路径开关，不是多一道独立威胁类型：true 时整段改走整行正则判定（模块 whole_line_regex.py），上表默认路径（shell_mismatch / python_name_kill / backend_pid_kill / 严格 worktree / 切段 safety）不跑。命中规则名 host_guard:whole_line_regex。整行路径内容：
  • 固定整行正则：杀 jiuwenswarm/jiuwenclaw；按名 Stop-Process/taskkill /IM 打 python、node、jiuwenswarm；pkill/killall python
  • 防自尽：命令目标 PID 为当前进程或父进程（或 runtime.protected_pids 注入的集合）→ DENY
  • 宽松 worktree：文本里出现 worktree add 且目标出 workspace → DENY（可误伤 echo worktree add ../x）；仅 bash/powershell/core.powershell 跑 worktree，mcp_exec_command 不跑
 taskkill /PID <本PID> /F · Stop-Process -Name python · taskkill /IM node.exe /F 
host_guard:
  enabled: true
  worktree_guard: true
  shell_mismatch: true
  python_name_kill: false
  backend_pid_kill: false
  protected_patterns:                # 可选；缺省用内置
    - pattern: '\bpkill\b[^\n\r;|&]*agent_server'
      reason: blocked: pkill agent_server
  whole_line_regex: false

11. 审计日志（agent_shield）

仅本库写出的日志契约 · 与 rail / 前端打的行无关 · 工具参数原文不落盘

库写什么
普通 Python logging，logger 名为 agent_shield.tool_permission.engine / agent_shield.tool_permission.manager。 消息正文是固定前缀 + key=value 字段；不指定文件名，落盘由宿主 Handler 决定。

11.1 事件一览

消息前缀何时要点
permission.manager.update update_config key=… replaced=True|False
permission.manager.remove remove_config key=… removed=…
permission.manager.unregistered_key 未登记 key 来 check warning；随后抛 KeyError
permission.engine.decision 每次 check_permission 合并后 主审计行（见下）
permission.engine.component_failed 某组件 evaluate 抛错 component=类名；异常继续上抛

11.2 decision 行：字段与可选值

permission.engine.decision key=… tool=… kind=… shell=… decision=… matched_rule=… winner=… basis=… components=[…]
字段可选值 / 形态含义
key 业务字符串 · default · (one-off) · 其它 label 引擎构造时的 label；Manager 登记键；一次性 config= 固定为 (one-off)
tool 任意工具名字符串 本次 check_permission 的工具名
kind original · unwrapped · subcommand 日志里取的是最后一个被评估的候选的类型（多候选时不一定等于「唯一原因」；定位看 decision/matched_rule/components）
shell True · False 该候选是否按 shell 路径处理（Python bool 的字符串形式）
decision allow · ask · deny 引擎最终结论（取最严合并后）
matched_rule 规则 id 字符串 · 或 None 与最终 decision 绑定的规则标签（如 tools.bash、tiered_policy:rules:deny:rules[deny_rm]）；组件放行但未挂规则 id 时可为 None
winner 组件类名 · 或 - 在有意见的组件里，第一个「permission 与 matched_rule 都与最终结果相同」的组件名；对不上则为 -
basis component · no_verdict · no_subscriber 结论怎么来的： component=至少有一个组件给出了非弃权意见并参与合并（常态）； no_verdict=问过组件但全是 none； no_subscriber=订阅列表为空（极端，正常路径少见）
components 见下方「怎么读」 必须整段展开：每个组件一次意见；定位「谁拦的 / 谁弃权」靠这里，不能省略

components 怎么读

固定组件顺序（每个候选一轮）：

InjectionComponent → CommandAllowlistComponent → DestructiveWarningComponent → TieredPolicyComponent → HostGuardComponent → FileGuardComponent → DeletionGuardComponent → ImmutableControlPlaneComponent → NetGuardComponent

  • 单项形态：组件类名=none（弃权）或 组件类名=allow|ask|deny 或 组件类名=allow|ask|deny(规则id)
  • 多候选（剥壳 / 子命令）时，按候选顺序把上述 9 项再追加一遍，所以列表会变长；对照时按每 9 个一组切
  • 排障：先看最终 decision + matched_rule + winner，再在 components 里找同规则/同等级的项；none 表示该组件本轮没说话

11.4 relay-claw 集成 jiuwenswarm 时日志在哪

AgentServer 启动时把 agent_shield.tool_permission 挂到滚动文件 permissions.log（另有控制台）。文件前缀形如：

2026-10-29 19:00:00.123 INFO agent_shield.tool_permission.engine: permission.engine.decision …
  • 路径：{LOG_ROOT_PATH}/permissions.log；未设环境变量时默认 ~/.jiuwenswarm/service_default/.logs/permissions.log（或 service_{sid}/.logs）。
  • relay-claw sidecar：拉起 AgentServer 时通常注入 LOG_ROOT_PATH=<数据目录>/service_default/.logs （数据目录来自 JIUWENSWARM_DATA_DIR / 兼容旧名 JIUWENCLAW_DATA_DIR）。 因此本机常见为：<JIUWENSWARM_DATA_DIR>/service_default/.logs/permissions.log。
  • 同文件里还可能有调用方带 [PermissionEngine] 的行——那是 rail 自己打的， 不是 agent_shield 契约；认引擎结论只搜 permission.engine.decision。
